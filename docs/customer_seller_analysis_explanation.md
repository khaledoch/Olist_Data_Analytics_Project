# Customer and Seller Analysis SQL Explanation

This query answers two questions at the same time: which customer cohorts are the most valuable and repeat-buying, and which sellers are generating the most delivered revenue. The analysis uses only delivered orders so the result reflects completed business rather than canceled or incomplete transactions.

The first part of the query builds a customer-level order value table. The `WITH customer_order_value AS (...)` block starts by selecting the `customer_unique_id`, the month of that customer's first purchase, the order ID, and the value of each delivered order.

```sql
WITH customer_order_value AS (
	SELECT
		customers.customer_unique_id,
		DATE_TRUNC('month', orders.order_purchase_timestamp)::date AS cohort_month,
		orders.order_id,
		SUM(order_items.price + order_items.freight_value) AS order_value
	FROM cleaned.olist_orders_dataset AS orders
	INNER JOIN cleaned.olist_customers_dataset AS customers
		ON orders.customer_id = customers.customer_id
	INNER JOIN cleaned.olist_order_items_dataset AS order_items
		ON orders.order_id = order_items.order_id
	WHERE orders.order_status = 'delivered'
		AND orders.order_purchase_timestamp IS NOT NULL
		AND customers.customer_unique_id IS NOT NULL
	GROUP BY
		customers.customer_unique_id,
		DATE_TRUNC('month', orders.order_purchase_timestamp)::date,
		orders.order_id
)
```

- `customers.customer_unique_id` identifies the same customer across all of their orders.
- `DATE_TRUNC('month', orders.order_purchase_timestamp)::date` converts every order date to the first day of its purchase month, so we can bucket each order into a monthly cohort.
- `orders.order_id` keeps each order separate so the aggregation happens at the order level before we summarize by customer.
- `SUM(order_items.price + order_items.freight_value)` creates the delivered order value, which matches the project rule of measuring revenue as product price plus shipping value.
- The join from `orders` to `customers` connects each order to the real customer record.
- The join from `orders` to `order_items` brings in the line-item rows, which is necessary because revenue lives on the item level.
- `WHERE orders.order_status = 'delivered'` restricts the analysis to only completed transactions.
- `AND orders.order_purchase_timestamp IS NOT NULL` removes rows with missing purchase timestamps, because a cohort needs a valid first-order date.
- `AND customers.customer_unique_id IS NOT NULL` removes incomplete customer records so the customer-level grouping is valid.
- `GROUP BY` keeps the result at the customer-by-order level, making each order a row in the temporary table before the next grouping step.

The second block creates the customer cohort base table. It takes the temporary customer_order_value table and calculates each customer's first purchase month, how many delivered orders they placed, and total revenue generated by that customer.

```sql
customer_cohort_base AS (
	SELECT
		customer_unique_id,
		MIN(cohort_month) AS first_purchase_month,
		COUNT(DISTINCT order_id) AS total_orders,
		SUM(order_value) AS total_customer_revenue
	FROM customer_order_value
	GROUP BY customer_unique_id
),
```

- `customer_unique_id` is the person-level key that defines the customer.
- `MIN(cohort_month)` picks the earliest purchase month for each customer, which becomes that customer's cohort month.
- `COUNT(DISTINCT order_id)` counts the number of delivered orders each customer has placed, avoiding double-counting if multiple items are tied to the same order.
- `SUM(order_value)` sums the revenue generated by that customer across all delivered orders.
- `GROUP BY customer_unique_id` collapses all orders into one row per customer, which is what we need before measuring cohort behavior.

The third block summarizes cohorts. It groups customers by their first purchase month and calculates cohort size, repeat customers, average order count, average revenue per customer, total cohort revenue, and repeat-customer rate.

```sql
customer_cohort_summary AS (
	SELECT
		first_purchase_month AS cohort_month,
		COUNT(*) AS cohort_customers,
		COUNT(*) FILTER (WHERE total_orders > 1) AS repeat_customers,
		ROUND(AVG(total_orders)::numeric, 2) AS avg_orders_per_customer,
		ROUND(AVG(total_customer_revenue)::numeric, 2) AS avg_revenue_per_customer,
		ROUND(SUM(total_customer_revenue)::numeric, 2) AS total_cohort_revenue,
		ROUND(
			100.0 * COUNT(*) FILTER (WHERE total_orders > 1) / COUNT(*),
			2
		) AS repeat_customer_rate_percent
	FROM customer_cohort_base
	GROUP BY first_purchase_month
)
```

- `first_purchase_month AS cohort_month` renames the cohort-defining month in a more readable way.
- `COUNT(*)` counts all customers in each monthly cohort.
- `COUNT(*) FILTER (WHERE total_orders > 1)` counts customers who bought more than once, which is the repeat-customer measure.
- `ROUND(AVG(total_orders)::numeric, 2)` calculates the average number of orders per customer within the cohort.
- `ROUND(AVG(total_customer_revenue)::numeric, 2)` calculates the average amount of revenue created per customer in that cohort.
- `ROUND(SUM(total_customer_revenue)::numeric, 2)` totals the value created by every customer in that cohort.
- `100.0 * COUNT(*) FILTER (WHERE total_orders > 1) / COUNT(*)` turns repeat count into a percentage so we can compare cohorts easily.
- `GROUP BY first_purchase_month` makes each monthly cohort its own group.

The final customer query selects and orders the cohort output.

```sql
SELECT
	cohort_month,
	cohort_customers,
	repeat_customers,
	avg_orders_per_customer,
	avg_revenue_per_customer,
	total_cohort_revenue,
	repeat_customer_rate_percent
FROM customer_cohort_summary
ORDER BY cohort_month;
```

- `cohort_month` shows the month when the customer first appeared.
- `cohort_customers` tells us how many customers joined in that cohort.
- `repeat_customers` tells us how many of those customers bought again.
- `avg_orders_per_customer` shows the typical order count within the group.
- `avg_revenue_per_customer` shows the typical value created by each customer in that cohort.
- `total_cohort_revenue` shows the total revenue generated by the full group.
- `repeat_customer_rate_percent` shows the share of the cohort that became repeat buyers.
- `ORDER BY cohort_month` keeps the cohorts in chronological sequence so trends are easy to read.

The second half of the query focuses on sellers. The first seller block calculates the delivered order value per seller and per order.

```sql
WITH seller_order_value AS (
	SELECT
		order_items.seller_id,
		orders.order_id,
		SUM(order_items.price + order_items.freight_value) AS order_value
	FROM cleaned.olist_order_items_dataset AS order_items
	INNER JOIN cleaned.olist_orders_dataset AS orders
		ON order_items.order_id = orders.order_id
	WHERE orders.order_status = 'delivered'
	GROUP BY order_items.seller_id, orders.order_id
),
```

- `order_items.seller_id` identifies the seller attached to each item row.
- `orders.order_id` keeps the order connected to the seller for the order-level aggregation.
- `SUM(order_items.price + order_items.freight_value)` measures the delivered value associated with each order for that seller.
- `WHERE orders.order_status = 'delivered'` keeps only completed transactions.
- `GROUP BY order_items.seller_id, orders.order_id` creates one row per seller-order combination so later seller totals are accurate even when one order contains multiple items.

The seller summary block aggregates each seller’s total delivered revenue and order count.

```sql
seller_summary AS (
	SELECT
		seller_id,
		COUNT(DISTINCT order_id) AS delivered_orders,
		ROUND(SUM(order_value)::numeric, 2) AS total_seller_revenue,
		ROUND(AVG(order_value)::numeric, 2) AS avg_order_value
	FROM seller_order_value
	GROUP BY seller_id
)
```

- `COUNT(DISTINCT order_id)` counts how many delivered orders each seller fulfilled.
- `ROUND(SUM(order_value)::numeric, 2)` totals the value generated by each seller in delivered orders.
- `ROUND(AVG(order_value)::numeric, 2)` shows the average order value per seller order.
- `GROUP BY seller_id` produces one row per seller.

The final seller query ranks sellers by business contribution.

```sql
SELECT
	seller_id,
	delivered_orders,
	total_seller_revenue,
	avg_order_value
FROM seller_summary
ORDER BY total_seller_revenue DESC, delivered_orders DESC
LIMIT 15;
```

- `seller_id` is the seller identifier.
- `delivered_orders` shows how many completed orders the seller was associated with.
- `total_seller_revenue` ranks the seller by total delivered revenue.
- `avg_order_value` helps distinguish a seller with many small orders from a seller with fewer but larger orders.
- `ORDER BY total_seller_revenue DESC, delivered_orders DESC` puts the biggest contributors first.
- `LIMIT 15` keeps the output focused on the strongest sellers without making the result too long for a portfolio query.

The main insight from this query is not about a single anomaly; it is about the shape of the marketplace. Customer cohorts show how many new buyers arrive each month and how many become repeat customers, while the seller ranking shows whether value is concentrated among a small set of suppliers. The logic stays consistent with the project’s overall rule: delivered orders define real business value, and freight is included in order value the same way it is in the earlier monthly analysis.
